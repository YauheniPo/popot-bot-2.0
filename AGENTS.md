Два независимых компонента: Hermes на VPS и Telegram User Info Bot.
Перед работой прочитай нужную страницу wiki ниже и вложенный `AGENTS.md`,
если он есть в затронутом каталоге. Не смешивай изменения компонентов без задачи.

## Имплементация и улучшения

- До правок определи проверяемый результат и самый простой рабочий подход.
  Для нескольких шагов дай короткий план с проверкой результата каждого шага.
  Существенные допущения называй явно; спрашивай, если выбор меняет scope,
  безопасность или совместимость. Безопасные обратимые детали решай самостоятельно.
- Сначала установи причину: прочитай реализацию, вызывающий код, конфиг и логи.
  Для регрессии добавь воспроизводящий тест, затем минимальный системный фикс.
- Каждая правка должна относиться к задаче. Не добавляй функции «на будущее»,
  одноразовые абстракции и непрошенную конфигурируемость; сохраняй стиль проекта.
  Удаляй ставшие ненужными из-за твоей правки импорты и код. Старый несвязанный
  dead code только отмечай, не включай его очистку в diff.
- Незнакомые API и команды проверяй по исходникам установленной версии или
  официальной документации через доступные инструменты; не выдумывай интерфейсы.
- Используй существующую архитектуру; не добавляй обходы авторизации,
  дублирующие сервисы, новые зависимости или массовые рефакторинги без согласования.
- Сохраняй совместимость API, пользовательские данные и настройки. Изменения
  VPS оформляй через managed Ansible/runtime, а не разовой правкой на сервере.
- Deploy должен быть идемпотентным: передавать только нужные изменения,
  не делать лишних рестартов и уведомлений. Политику backup не ослабляй сам.
- Workspace и официальный Dashboard используют существующий Hermes backend
  и общий home. Соблюдай разделение UI-owned настроек и Ansible/Vault policy.
  Метрики публикуются в Prometheus/Grafana; удалённую панель `/ops` не возвращай.
- Модели, порты, лимиты и версии бери из конфигурации, не дублируй в коде.
  OpenRouter — только доступные free-модели; не включай платный fallback.
  Сохраняй `PR_REVIEWER=0`, пока пользователь явно не попросит изменить его.
- Для внешних вызовов предусматривай таймауты, ограниченные осмысленные retries
  и понятный прогресс без секретов. Heartbeat не доказывает, что провайдер думает.
  Не обещай фоновый результат без проверенного механизма возврата в исходную сессию.
- Замечания AI review и Sonar проверяй по текущему коду и сценарию сбоя.
  Исправляй подтверждённое; false positive объясняй доказательствами.
  Не меняй корректное поведение ради сомнительного замечания или зелёного gate.

## Проверки и сдача

- «Готово» означает проверенный результат в оговорённом scope. Не скрывай
  недоделки за TODO, фиктивными успешными ответами, пустым catch или отключением
  падающих тестов. Моки допустимы в тестах, но не заменяют реализацию.
- Тестируй контракты и поведение, включая ошибки, повторный запуск и отмену.
  Не привязывай тесты к изменяемым дефолтам моделей/версий/лимитов;
  проверяй подстановку значений и обязательные инварианты безопасности.
- Запускай проверки затронутого компонента: `bash hermes/check.sh` для Hermes;
  для бота — `python -m unittest discover -s tests -v` из `telegram-user-info-bot`.
  Для Ansible — также syntax-check, для CI — соответствующие тесты `.github/scripts`.
  Перед сдачей проверь diff и `git diff --check`; отсутствие инструмента не равно успеху.
- Отвечай по-русски, кратко: что изменено, что реально проверено, что осталось.
  Укажи команды и итоги проверок без полного дампа логов; недоступные проверки
  и известные ограничения назови явно. Отличай локальные тесты от live-проверки;
  явно указывай необходимость deploy.

## Общение

- Начинай с результата или существенного риска, без похвалы и вводных фраз.
  Отделяй факт от вывода и предположения; метки `[Точно]`, `[Скорее всего]`,
  `[Догадка]` используй, когда они помогают, а не перед каждым предложением.
- Возражай по существу: конкретная причина, риск и более простой вариант.
  Не соглашайся ради комфорта и не спорь для вида; пересматривай выводы по новым
  фактам. Объясняй решения и доказательства, не требуй раскрытия внутреннего reasoning.

## Границы действий

- Не делай commit, push, PR, deploy или изменение production без явного запроса.
  Запрос commit не разрешает push. Работай в текущей ветке, сохраняя чужой diff/index;
  не делай reset, force-push и удаление данных без отдельного разрешения.
- Секреты — только Vault/разрешённое окружение. Не выводи и не сохраняй в Git
  ключи, cookies, OAuth, содержимое `.env`, расшифрованного Vault или backup.
  Не отключай TLS/auth, не открывай публичные порты и не ослабляй SSH ради фикса.
- Ограничение sandbox не разрешает его обход. Используй разрешённый механизм
  согласования либо сообщи точный блокер; не отключай защиту автоматически.
- Названия веток, commit messages и PR descriptions — на английском.
  Для созданных тобой commit messages и PR descriptions добавляй собственный
  `Assisted-by:` trailer с именем агента. Не создавай их без запроса.
