# Workspace рядом с официальной панелью Hermes

[Hermes Workspace](https://github.com/outsourc-e/hermes-workspace) устанавливается
отдельной native systemd-службой `hermes-workspace.service`, но использует
существующие gateway, официальный dashboard и `/home/hermes/.hermes`.
Второй gateway/Telegram polling не запускается. Официальная панель остаётся
на своём адресе; Workspace добавляет свой UI, Office и операции с рабочими файлами.

## Записи фоновых запусков в чате

Панель **Chat run records** (раньше **Background runs**) показывает сохранённые
незавершённые записи Workspace, а не список процессов VPS или Telegram-агентов.
Каждая строка содержит сессию, короткий run ID, время последнего сохранения и
последний сохранённый статус/вывод. Несколько `main` — разные запуски одной сессии.

- **Local stream registered**: текущий процесс Workspace зарегистрировал stream
  запроса. Это не доказательство прогресса модели или активности CI.
- **No local stream; task state unknown** / **unconfirmed**: локальной регистрации
  нет. Причиной может быть перезапуск, разрыв соединения или завершение stream;
  сохранённый `active` не означает, что задача до сих пор выполняется.
- **Dismiss record** доступна после 5 минут без обновлений при отсутствии локального
  stream. После подтверждения запись скрывается, но её история и статус не меняются.
  Это **не остановка агента**. Сервер проверяет актуальность записи в очереди записи;
  если пришло новое событие, вернёт `409` и предложит обновить список.
  Новое событие после скрытия снова делает запись видимой. Автоудаления истории нет.

**Open chat** открывает исходную сессию. При ошибке API панель показывает ошибку,
считает отображаемые сведения устаревшими и временно запрещает скрытие записей.
Опрос идёт через 10 секунд после завершения предыдущего, с таймаутом 15 секунд;
при уходе со страницы запрос отменяется. Исправление применяется обычным deploy:
Ansible пересобирает Workspace при изменении managed-адаптера.

## Голосовые сообщения и язык распознавания

В `Settings → Voice` поле **Recognition language** доступно для всех
STT-провайдеров, включая **Nous (Hermes gateway)**. Пустое значение или `auto`
при уходе из поля сохраняется как `stt.language: ""`: язык записи определяется автоматически,
русскую речь не нужно принудительно распознавать как английскую.
`ru` полезен только для заведомо русскоязычных записей. Настройки
`stt.<provider>.language` и переменная `HERMES_LOCAL_STT_LANGUAGE` могут
переопределить автоопределение — проверяйте их, если язык всё ещё неверный.

Deploy восстанавливает общий `stt.language: ""`, сохраняя выбранного
провайдера, модель и пользовательский словарь. Это намеренное исключение:
чтобы закрепить другой общий язык после deploy, меняйте
`vps_hermes.config.managed_overlay.stt.language` в `config/vps-defaults.yml`.
**Speech vocabulary** сохраняет короткую подсказку `stt.prompt` при уходе
из поля: имена, названия и термины, например `Hermes, Tailscale, Playwright`.
Это контекст для поддерживающих его провайдеров, не инструкция переводить
и не гарантия дословной точности. Ошибка сохранения не отображается как `Saved`.

Голосовые Telegram обрабатывает Hermes. В закреплённой версии Workspace
собственный браузерный микрофон поддерживает удалённое распознавание через
OpenAI/Groq, но **не Nous**; наличие Nous в настройках не добавляет этот маршрут.
Новый платный провайдер автоматически не включается. Правило ответов Hermes
сохраняет язык голосового сообщения и требует уточнять важные неясные слова,
а не додумывать их. Оно не может восстановить уже испорченный STT текст.

После deploy проверьте новые голосовые на русском и другом языке: транскрипт
должен оставаться на языке записи. Отдельно проверьте имена, отрицания и числа;
для неоднозначной команды агент должен запросить уточнение. Качество STT нужно
проверять на реальных записях, а не только на прохождении тестов конфигурации.

## Доступ и первая установка

В `config/vps-defaults.yml` включён `vps_deploy.features.workspace_ui`.
Настройки установки находятся в `vps_workspace_ui`: исходники закреплены
commit SHA, pnpm — версией, зависимости устанавливаются с `--frozen-lockfile`.
Версии обновляются явно через deploy, не автоматически при старте службы.
Требуется установленный Hermes Node >= 22. Upstream all-in-one installer,
`start:all` и отдельная установка Hermes не используются.

При включённом Workspace Ansible устанавливает системные пакеты `zsh` и `tmux`:
закреплённый `/swarm` явно запускает `zsh` для shell-терминалов, а `tmux` нужен
для терминальных сессий воркеров. До запуска UI deploy проверяет `zsh --version`
и `tmux -V` от пользователя `hermes` с тем же `PATH`, что у службы. Проверки
ограничены по времени, ошибки не скрываются. Login shell пользователя не
меняется. При `vps_workspace_ui.swarm.enabled: true` создаются управляемые
профили, а `swarm.start_workers: true` запускает отсутствующие tmux-сессии
после готовности Workspace. Зависимости
проверяются и при повторном deploy с уже собранным Workspace.

Если ранее терминал завершался с `FileNotFoundError` после
`command: zsh -lc exec zsh -l` или показывал `tmux not installed`, примените
deploy с этими изменениями, обновите `/swarm` и заново откройте терминал.
Завершившаяся PTY-сессия сама не восстановится. Установка пакетов исправляет
отсутствие исполняемых файлов. Управляемый Swarm описан ниже; автоматического
подключения нативных Telegram-субагентов к нему нет.

1. В зашифрованном `ansible/group_vars/all/vault.yml`, в `hermes_secret_env`,
   добавьте `API_SERVER_KEY` и `HERMES_WORKSPACE_PASSWORD`: два независимых
   значения минимум по 4 символа. Допускаются буквы, цифры, Unicode,
   спецсимволы и пробелы — пробелы не обрезаются. В YAML заключайте значения
   в кавычки, особенно состоящие только из цифр. Длинные случайные значения
   безопаснее: например, `openssl rand -hex 32`. Не сохраняйте секреты в Git.
2. Сохраните существующие provider/Telegram credentials в том же Vault.
3. Из корня репозитория запустите обычный deploy:

   ```bash
   ANSIBLE_CONFIG=hermes/ansible/ansible.cfg ansible-playbook \
     -i hermes/ansible/inventory.ini hermes/ansible/playbook.yml --ask-vault-pass
   ```

Workspace доступен на `https://<VPS-Tailscale-hostname>:3002` с паролем
`HERMES_WORKSPACE_PASSWORD`. Нужны подключение к tailnet, разрешение ACL на этот
порт и включённый Tailscale HTTPS. Публичные firewall-порты не открываются.
Официальный dashboard остаётся на HTTPS 443 и использует свою авторизацию.

Workspace слушает только `127.0.0.1:3002`, gateway API — `127.0.0.1:8642`.
Служба получает API token и пароль из общего `.env` при запуске, а не из
frontend bundle или текста unit-файла. Авторизация Dashboard — отдельная:
`API_SERVER_KEY` подходит для Gateway API, но не заменяет сессию Dashboard.
Secure cookies включены: используйте HTTPS Tailscale, а не обычный HTTP-туннель.
Публичный multiplayer hub при сборке отключён.

### Вход в Dashboard и ошибка `401 no_cookie`

На закреплённом Hermes Dashboard использует OAuth-сессию. Закреплённый
Workspace сам по себе ищет старый токен в HTML и не передаёт cookies браузера,
поэтому успешный вход с паролем Workspace ещё не открывает Dashboard API.

После deploy:

1. Откройте `https://<VPS-Tailscale-hostname>/login` (HTTPS **443**) и войдите
   в официальный Dashboard через его штатного провайдера.
2. В том же браузере откройте `https://<тот-же-hostname>:3002`, войдите с
   `HERMES_WORKSPACE_PASSWORD` и обновите страницу. Если раздел отмечен
   недоступным после старого probe, нажмите **Reconnect**.
3. Проверьте Sessions, Skills и Jobs. В Network ответы этих API не должны
   содержать `401 no_cookie`. Не копируйте cookies или токены в чат/конфиг.

Managed launcher создаёт отдельный entry-файл, не изменяя исходники upstream.
Общий серверный адаптер передаёт только `__Host-hermes_session_at`,
`__Host-hermes_session_rt` и `__Host-hermes_session_provider` текущего запроса
в **точный loopback origin Dashboard**. Это работает для всех HTTP-методов
и путей Dashboard, включая запись. Для MCP отдельный адаптер переводит
контракты Workspace в штатные маршруты Hermes (см. ниже).
Cookies Workspace, Grafana и code-server не передаются. Обновлённые cookies
Dashboard возвращаются браузеру отдельными `Set-Cookie` с Secure/HttpOnly;
они не сохраняются в файлы и не подменяют пароль Workspace.

Одновременные обращения одной сессии сериализуются до получения заголовков,
чтобы не обновлять один refresh token параллельно. Мост хранит не более 256
сессионных ключей в памяти; каждый ключ удаляется через 30 секунд без продления
при чтении. Потоки ответов не буферизуются и не обрываются этим сроком.
Сессии разных браузеров не смешиваются; фоновая работа после завершения
HTTP-запроса не получает его credentials. Внешние перенаправления не следуются
с cookies. Проверки OAuth и авторизация Workspace остаются включёнными.

Оба UI должны использовать один hostname: cookies не привязаны к порту,
но не переносятся с IP на DNS-имя или между разными браузерами. При истечении
авторизации ошибка содержит ссылку на официальный `/login`, а не рекомендацию
переустановить gateway. Мост не координирует refresh с вкладкой самого Dashboard:
при конфликте ротации войдите повторно и обновите обе панели.

Чат `/v1/chat/completions` продолжает обращаться к Gateway с API token,
включая streaming. Локальные операции Workspace с Hermes home/PTY остаются
штатными. Адаптер не добавляет отсутствующие в Hermes API и не подключает
Telegram-субагентов к Swarm автоматически. Background jobs не получают
постоянный OAuth-доступ за счёт чужой браузерной сессии.

### MCP Servers: штатный API Hermes

Закреплённый Workspace ожидает `/api/mcp`, а Hermes предоставляет
`/api/mcp/servers`. Managed MCP-адаптер выполняется только на сервере Workspace
и использует тот же защищённый Dashboard API с cookies текущего пользователя:

| Действие Workspace | Штатный запрос Hermes |
|---|---|
| Список и создание | `GET/POST /api/mcp/servers` |
| Enable/Disable | `PUT /api/mcp/servers/{name}/enabled` |
| Test сохранённого сервера | `POST /api/mcp/servers/{name}/test` |
| Удаление | `DELETE /api/mcp/servers/{name}` |

Пустой список серверов — успешный ответ, а не отсутствие MCP. При первом
обращении к Gateway Status или MCP после входа адаптер повторяет штатный
защищённый `/api/gateway-reprobe`: стартовая проверка без браузерных cookies
больше не оставляет MCP недоступным до ручного Reconnect. Параллельные проверки
одного браузера объединяются; успешный результат ограничен двумя минутами,
отрицательный — пятью секундами. Авторизация Workspace не обходится.

В managed-сборке все MCP-операции направляются в Dashboard независимо от
общего probe `/api/status`. Его временная ошибка/таймаут не перенаправляет
список, создание, Test, Enable/Disable или Delete в Gateway `:8642`, где MCP
маршрутов нет (раньше это приводило к `502: MCP list failed (404)`).
Доступность MCP по-прежнему проверяется отдельно; cookies и нативные ошибки
Dashboard не обходятся, операции записи не повторяются на другом backend.
Изменение build-wrapper автоматически вызывает пересборку при обычном deploy;
простого обновления вкладки до deploy недостаточно.

Поддерживаются stdio command/args/env и HTTP URL, включая Bearer token.
Нативная проверка полей/команд остаётся в Hermes; токен передаётся через
`bearer_token`, а не сохраняется адаптером. Секретные env в списке маскируются.
Выбор разрешённых инструментов не выдаётся за список обнаруженных инструментов:
реальные инструменты возвращает Test. Адаптер не заменяет всю карту
`mcp_servers` и не перезапускает gateway/Telegram. Enable/Disable применяется
согласно правилам Hermes — уже работающая сессия может потребовать перезапуска.

Карточка показывает `—`, если сервер ещё не проверен, выключен, проверка
не удалась или результат устарел. После **Test** список получает статус и
реальное число инструментов, включая корректный `0`, если сервер вернул пустой
список. `Last test` — время последней проверки, **не live-мониторинг**.
Результат хранится в памяти Workspace до 5 минут, отдельно для каждого профиля,
сбрасывается при изменении видимой конфигурации, удалении, переключении enabled
или рестарте Workspace. После замены только секрета также нажмите Test:
замаскированные значения API не позволяют обнаружить такую замену по списку.
Открытие/обновление страницы не запускает MCP-процессы.

Managed build-wrapper исправляет отображение без правки tracked-файлов upstream;
изменение UI-адаптера инвалидирует build marker и вызывает пересборку на deploy.
Серверный адаптер корректирует только два известных ошибочных пресета pinned
Workspace, в том числе уже скопированных в его preset store:

- **Fetch:** `uvx mcp-server-fetch`, согласно
  [официальной инструкции](https://github.com/modelcontextprotocol/servers/tree/main/src/fetch).
  npm-пакет `@modelcontextprotocol/server-fetch` использовать нельзя.
- **GitHub:** официальный HTTP endpoint `https://api.githubcopilot.com/mcp/readonly`
  с bearer PAT; [документация GitHub](https://github.com/github/github-mcp-server/blob/main/docs/remote-server.md).
  `server-everything` — демонстрационный MCP, а не GitHub.
- **Memory:** существующий пресет не меняется. `Auth: none` у stdio означает
  отсутствие HTTP/OAuth-аутентификации, а не отсутствие env-секретов.

При включённом Workspace deploy добавляет отсутствующие настройки кэша в
`env` stdio-серверов: для npm/npx — `npm_config_cache` внутри
`$HERMES_HOME/.cache/mcp/npm`, для uv/uvx — `UV_CACHE_DIR` и
`UV_PYTHON_INSTALL_DIR`, `UV_TOOL_DIR`, `UV_TOOL_BIN_DIR` внутри `.cache/mcp`,
а также `$HERMES_HOME/bin` в PATH.
Это нужно задавать именно в server `env`: Hermes фильтрует окружение дочерних
процессов. Dashboard остаётся с `ProtectSystem=strict` и прежним
`ReadWritePaths=$HERMES_HOME`; открывать весь `/home/hermes` на запись не нужно.
Явные env-переопределения и HTTP-серверы сохраняются. Новые серверы, добавленные
между deploy, должны получить эти env через UI, если им нужны npm/uv-кэши.

Для Memory MCP задавайте постоянный `env.MEMORY_FILE_PATH` вне npm-кэша,
например `$HERMES_HOME/mcp-memory.jsonl` (абсолютный путь). Перед изменением
пути перенесите существующий граф: обычный deploy не мигрирует и не удаляет его.
Этот граф не заменяет Hermes `memories/MEMORY.md` и `USER.md`.

Команды уже сохранённых **серверов** обычный deploy не переписывает. Для исправления
именно этих двух ошибочных записей добавьте в `hermes_secret_env` зашифрованного
Vault ключ `MCP_GITHUB_API_KEY` с GitHub PAT, ограниченным нужными репозиториями
и правами чтения, затем запустите обычный полный deploy из `hermes/`:

```sh
ANSIBLE_CONFIG=ansible/ansible.cfg ansible-playbook \
  -i ansible/inventory.ini ansible/playbook.yml \
  --ask-vault-pass --ask-pass \
  -e hermes_repair_workspace_mcp_presets=true
```

Ремонт применяется только при `workspace_ui: true` и точном совпадении известных
ошибочных команд/аргументов, идемпотентен и сохраняет enabled/tool filters и
остальной config. Из GitHub-записи убирается старый stdio PAT; вместо него
сохраняется ссылка `${MCP_GITHUB_API_KEY}` на Vault-managed `.env`, не значение
секрета. Без нового ключа ремонт GitHub завершается ошибкой до записи config.
Используйте существующий backup deploy для отката; во время deploy не редактируйте
конфиг в UI. `uvx` должен быть доступен пользователю Hermes (включая
`$HERMES_HOME/bin`) — deploy проверяет
это без установки или запуска Fetch. Нестандартные команды, URL, headers или
дополнительные env не переписываются: настройте такой сервер вручную в Dashboard.
После deploy обновите Workspace и нажмите Test у каждого сервера. Количество
инструментов не задаётся заранее: реальное подключение всё ещё может завершиться
ошибкой из-за доступа к провайдеру, токена или отсутствующего runtime.

Ограничения закреплённых версий: Test/Discover несохранённого сервера,
пользовательские HTTP headers, OAuth client settings, создание сразу disabled
и изменение tool filters из Workspace возвращают явную ошибку `422`.
Поток логов отдельного MCP-сервера не реализован в этом API (`501`).
Сначала сохраните сервер, затем используйте Test. OAuth-вход/повторную
авторизацию и расширенную конфигурацию выполняйте в официальном Dashboard;
кнопка OAuth Workspace не реализует штатный OAuth flow Hermes.
Нативные OAuth endpoints не переписываются. Поля, которых нет в native create,
не игнорируются молча и не применяются через небезопасную замену всего конфига.

После deploy проверьте вход в оба UI, открытие MCP Servers (в том числе пустого
списка), затем создание **доверенного** сервера → Test → Disable → Delete.
Test действительно подключается к MCP/запускает stdio-команду, поэтому это
не read-only проверка. Не используйте произвольные команды/чужие серверы.

При включённом Workspace значение `API_SERVER_KEY` из Vault преобразуется
в SHA-256 (UTF-8 → hex) перед записью `.env`: сам Hermes требует минимум
16 символов, а HTTP Bearer token должен быть совместим с заголовками.
Workspace автоматически читает полученный токен из общего `.env`;
`HERMES_WORKSPACE_PASSWORD` используется без изменения. Другим API-клиентам
нужен именно полученный токен. При переходе со старой конфигурации, где
ключ копировался напрямую, токен изменится — обновите такие клиенты.
Хеширование не добавляет энтропию: четыре символа остаются слабым секретом.
При отключённом Workspace API-ключ из Vault копируется без преобразования
и должен соответствовать требованиям самого Hermes.

## Memory: SOUL и инструкции AGENTS

Страница `/memory` показывает и редактирует настоящие файлы Hermes:

- `SOUL.md`, `AGENTS.md` и дополнительные `AGENTS.<name>.md` в Hermes home;
- `workspace/AGENTS.md` и вложенные инструкции — префикс `workspace/` означает
  `hermes_workspace` из Ansible (на VPS `/home/hermes/workspace`), не копию в home;
- `profiles/<role>/SOUL.md`, инструкции в корне профиля и `AGENTS*.md`
  внутри `swarm/worktrees/`;
- существующие `profiles/<role>/memories/MEMORY.md` и `USER.md` — отдельная
  память профиля, не копия и не ссылка на общую память;
- прежние `MEMORY.md`, `USER.md`, `memory/` и `memories/`.

В `workspace/AGENTS.md` общие правила из `hermes/instructions/common.md` и
возможности окружения находятся в отдельных блоках `HERMES MANAGED COMMON`
и `HERMES MANAGED ENVIRONMENT`. Редактор помечает их как managed наряду с
Ansible-интеграциями. Их правки через UI будут заменены при deploy (в Docker —
при следующем старте из image); личные дополнения сохраняйте вне маркеров.

В списке и поиске виден относительный путь, чтобы отличать основной файл от
проектных и профильных. Отображение дополнительного файла не подключает его
автоматически к prompt: применимость зависит от cwd и штатных правил Hermes
(например, `AGENTS.override.md` имеет приоритет над `AGENTS.md` в каталоге).
При открытии файла редактор показывает профиль, назначение, число Unicode-символов,
названия Ansible-managed блоков и правила применимости. Для нативных файлов памяти
показывается соответствующий явно настроенный `memory_char_limit`/`user_char_limit`
из конфигурации именно этого профиля. Если значение отсутствует или конфигурация
недоступна, UI пишет `unknown`, не угадывает дефолт и не подставляет лимит другого
профиля. В конфигурацию редактор не пишет; секреты из неё в ответ не включаются.
Счётчик учитывает весь файл, включая разделители, а не токены или фактический
снимок памяти. Превышение — предупреждение, не автоматическое удаление текста
и не увеличение лимита. Лимит редактора 512 KiB — отдельная защита.
`Loaded in this session: unknown` намеренно не обещает, что уже запущенный агент
перечитал файл. Для произвольного cwd UI показывает условие применимости, а не
выдаёт список файлов за фактический system prompt.
Исходники установленного Hermes, `.git`, `node_modules`, backup и symlink-файлы
не включаются. Допустимы только перечисленные виды Markdown-файлов, не `.env`
или произвольный путь. Размер файла ограничен 512 KiB, обход — 30 000 элементов
и 20 уровней; при превышении лимита каталогов возвращается явная ошибка.

Доступ требует входа в Workspace; запись сохраняет штатную проверку JSON/CSRF.
Редактор работает с существующими файлами. Перед изменением создаётся приватная
копия `{path, content}` в `$HERMES_HOME/.memory-editor-backups/<uuid>.json`.
Если файл изменён с момента начала редактирования, сохранение возвращает `409`:
сохраните свой текст отдельно, перечитайте файл и объедините изменения.
Это защита от обычных устаревших вкладок, не межпроцессная блокировка Ansible;
не редактируйте файлы во время deploy.

Изменения применяйте в новой сессии Hermes. Личные части инструкций сохраняются,
но Ansible восстанавливает свои managed-блоки при deploy. В `SOUL.md` Swarm-ролей
блок `ANSIBLE MANAGED SWARM ROLE` формируется из `vps_workspace_ui.swarm.workers`;
личные дополнения **вне блока**, например под `Personal additions`, сохраняются.
Для постоянного изменения самого managed-блока меняйте политику в репозитории.
При миграции старого целиком управляемого SOUL нестандартный текст сохраняется
вне нового блока; проверьте его на устаревшие или дублирующие инструкции.

### Что и кто запоминает

`USER.md` хранит устойчивые предпочтения пользователя; `MEMORY.md` — проверенные
долговременные факты и решения с источником, а для изменчивых фактов — датой.
Процедуры и ограничения относятся к `AGENTS.md`, стиль и роль — к `SOUL.md`.
Временные статусы, полные логи и промежуточные гипотезы оставляйте в задачах.
Не дублируйте одну инструкцию во всех файлах. Текст памяти не даёт разрешений
на действия и не отменяет текущий запрос пользователя.

Главный агент передаёт команде компактный `context`: язык, относящиеся к задаче
предпочтения, проверенные факты/источники/даты, неопределённости, пути инструкций
и разрешённые действия. Этот контекст сохраняется и передаётся каждому этапу;
плагин не читает и не копирует всю личную память автоматически.
Native delegates запускаются без памяти основного агента и без его SOUL;
проектные AGENTS могут быть включены штатным механизмом по рабочему каталогу.
Воркеры предлагают записи для памяти внутри результата с источником и датой.
Основной агент проверяет, устраняет противоречия и сохраняет через native memory
tool. Запрет общей записи для ролей — инструкция, не файловая изоляция ОС.

Deploy обновляет ролевые managed-блоки SOUL, но не создаёт общую writable память,
не переписывает личные `USER.md`/`MEMORY.md` и не увеличивает их лимиты.
Смысловое сокращение уже существующей памяти — отдельная проверяемая операция
с резервной копией, а не побочный эффект обновления инструкций.

### Profiles и Operations: описания и настоящий промпт

`/profiles` показывает описание из конфигурации профиля. Provisioning заполняет
отсутствующее описание Researcher/Builder/Reviewer из `swarm.workers.*.description`
(или роли и instructions), но не затирает непустые пользовательские описания.

На этом VPS Workspace и Hermes используют общий home. Список профилей читается
локально, включая `SOUL.md`, а не из сокращённого Dashboard-ответа. Для отдельного
удалённого backend остаётся upstream fallback; локальный текст ему не приписывается.

В `/operations` редактор показывает источник `profiles/<роль>/SOUL.md` (или
`SOUL.md` основного профиля). Save использует тот же авторизованный Memory API,
проверяет исходный текст и версию, сохраняет backup и **не создаёт второй промпт
в `config.yaml`**. Описание и промпт с сервера имеют приоритет над устаревшим
`localStorage` браузера. Пробелы и переводы строк SOUL сохраняются без trim.
При `409` сохраните черновик отдельно и перечитайте файл; не редактируйте во время deploy.

Существующие профили с явно заданным `config.yaml.system_prompt` сохраняют прежнее
поведение и помечаются `legacy config.yaml`: этот текст не удаляется и не мигрирует
молча. Новые управляемые Swarm-профили не копируют описание/system_prompt основного
профиля. Изменение одного промпта в Operations не перезаписывает модель.
Для применения инструкций начните новую сессию; занятых воркеров не перезапускайте.

## Кто управляет настройками

| Настройки | Источник и поведение deploy |
|---|---|
| Основной provider/model, модель делегирования и cron по умолчанию | Единый источник `vps_hermes.config.managed_overlay.model`; повторно применяется при каждом deploy |
| Остальные параметры model/cron, fallback, auxiliary, compression, memory limits, display, session reset | Общий `config.yaml`; существующие значения сохраняются, отсутствующие инициализируются из репозитория |
| Approvals, ограничения инструментов, disabled skills, сеть и bind/порты | Политика Ansible повторно применяется при deploy |
| API keys, токены, пароль Workspace | Vault → общий `.env`; изменения `.env` через UI будут заменены при deploy |
| Sessions, память, skills, OAuth | Существующий Hermes home; отдельная копия для Workspace не создаётся |
| Layout, Office и другие собственные настройки Workspace | Хранилища upstream Workspace; это не новые параметры конфигурации ядра Hermes |

Список сохраняемых разделов — `vps_hermes.config.ui_owned_sections`.
Исключение внутри `model` и `cron` — provider/model: они всегда управляются
репозиторием, даже если раздел включён в этот список.
Чтобы снова управлять конкретным разделом из репозитория, исключите его из
списка и примените deploy. При выключенном `workspace_ui` действует прежняя
политика Ansible для всех managed-параметров. Произвольные параметры Workspace
не становятся автоматически поддерживаемыми глобальными параметрами Hermes.

Workspace работает от пользователя `hermes`, поэтому это доверенная
административная панель с доступом к его файлам, терминалу и секретам, а не
изолированный viewer. Политика Ansible — восстановление значений при deploy,
не запрет администратору менять их между deploy. Не меняйте backend URLs/home
в Connection Settings: интеграция рассчитана на один локальный backend.
Не используйте кнопки установки/обновления Hermes или `Start Agent` в Workspace:
это upstream standalone-действия, они не управляют нашим systemd-unit и могут
запустить отдельный процесс. Обновления выполняйте Ansible, gateway при
необходимости перезапускайте через `systemctl restart hermes-gateway.service`.

Оба UI используют общий файл, но upstream не предоставляет межпроцессную
блокировку сохранений: не сохраняйте настройки одновременно в двух вкладках
разных панелей. Во время применения runtime-конфига Ansible останавливает оба
UI; ранее работавшие службы запускаются обратно и при ошибке в этом блоке.
Часть глобальных изменений требует перезапуска gateway и не меняет уже
работающие сессии; переопределение модели в Telegram topic сохраняет приоритет.

Первый deploy собирает Node-приложение и будет дольше обычного. Повторный
использует успешную сборку того же commit/pnpm/UI adapter. Workspace перезапускается
handlers при изменении сборки, unit/launcher/dashboard bridge/MCP adapter или managed `.env`.
Gateway использует существующий единый handler перезапуска.

### Skills выбранного профиля

В `/skills` выбор профиля читает его список через штатный Dashboard API
`GET /api/skills?profile=<name>`. Переключатель enabled отправляет
`PUT /api/skills/toggle` с явным `profile` в JSON: меняется `skills.disabled`
только выбранного профиля. Workspace использует существующую авторизованную
сессию Dashboard; обхода авторизации или fallback на основной профиль нет.

Ошибка загрузки показывается с кнопкой **Retry**, а не как `No skills found`.
Пустой список означает успешный ответ без подходящих skills, а не ошибку API.
Каталоги skills и списки disabled у профилей остаются раздельными; эта правка
не копирует skills основного агента воркерам. Установка и удаление через UI
сохраняют upstream-ограничение на активный профиль.
Изменение build-adapter применяется после deploy и пересборки Workspace.

### Единая модель агентов и Swarm

Для смены модели измените только `provider` и `default` в
`vps_hermes.config.managed_overlay.model` и примените deploy. Runtime использует
эту пару для главного агента, `delegation.provider/model`, `cron.model_provider/model`
и существующих `profiles/*/config.yaml`. Остальные параметры профилей, credentials,
история и память сохраняются. Повторное применение не перезаписывает совпадающие
профили. Symlink-профили/конфиги отклоняются, чтобы не записывать за их пределами.

Managed build-adapter Swarm берёт модель из общего `config.yaml` для списка ролей
и разрешения модели при запуске/dispatch. Шаблонные `GPT-5.5` и выбор другой
модели в roster больше не переключают воркера на постороннего провайдера.
Новые managed-профили инициализируются копией общего конфига provisioning-скриптом;
за создание и запуск отвечает отдельная настройка `vps_workspace_ui.swarm`. Исходники upstream
не переписываются, изменение адаптера автоматически вызывает пересборку.

Это политика значений по умолчанию, не миграция истории: уже запущенные воркеры
нужно остановить/запустить заново после смены модели. Явные переопределения
Telegram topic и отдельных cron-задач сохраняются; для единой модели также
снимите эти pins. Compression/vision/review auxiliary и аварийные fallback
не являются Swarm-воркерами и сохраняют отдельные маршруты.

### Управляемые Researcher, Builder и Reviewer

`vps_workspace_ui.swarm` задаёт роли, исходный repository_dir и запуск при deploy.
По умолчанию Researcher исследует, Builder меняет код и запускает тесты,
Reviewer независимо проверяет **явно переданный diff Builder**. Reviewer не
получает изменения автоматически: у каждого своя рабочая копия.

- Профили: `$HERMES_HOME/profiles/<role>`; config и история раздельные,
  `.env`/`auth.json` используют локальные ссылки на общий защищённый home.
- Worktree: `$HERMES_HOME/swarm/worktrees/<role>`, detached HEAD исходного
  репозитория на момент создания. Deploy не делает reset/pull существующих
  worktree и сохраняет незакоммиченные изменения. Обновление базы — отдельное
  явное действие после завершения задач.
- Скрипты запуска: `$HOME/.local/bin/<role>`. Roster хранится вне source checkout:
  `$HERMES_HOME/swarm/swarm.yaml`. Шаблонные десять ролей upstream не используются.
  Upstream сохраняет оперативные checkpoint/mission-файлы в
  `<repository_dir>/.runtime/`; это служебные данные, не изменения исходного кода.
  Не добавляйте их в коммит.
- Сессии: `swarm-researcher`, `swarm-builder`, `swarm-reviewer`. Создание tmux
  ещё не означает готовность: dispatch ждёт приглашение Hermes до 40 секунд,
  передаёт multiline через bracketed paste и не считает `IN_PROGRESS` итогом.
- `approvals.mode: manual`, без `--yolo/--ignore-rules` в fallback-dispatch.
  Инструкции запрещают самовольные commit/push/deploy и внешние сообщения.
  Роли и worktree — **не sandbox**: это один Unix-пользователь с общими правами.

Откройте `/swarm`, выберите роль и отправьте ограниченную задачу. Готовность
проверяйте по терминалу (`ready`) и реальному ответу/checkpoint, не только карточке.
Не отправляйте вторую задачу занятому воркеру. После разработки передайте Reviewer
пути Builder worktree и изменённых файлов, цель и критерии проверки.
Автономный orchestrator/autopilot не включается. После перезагрузки VPS или
завершения tmux запустите воркера через Start; очередной deploy также запускает
отсутствующие сессии. Рестарт Workspace может остановить созданные им tmux-процессы;
перед обновлением завершите задания. Не прерывайте активные воркеры ради deploy.

### Swarm Outputs / Reports: история, не проверка готовности

**Recent swarm activity** показывает последний известный runtime-снимок,
сессию или содержательную строку лога каждого профиля, включая основной
Workspace. Routine `INFO hermes_cli.mem_trim` скрыт, WARNING/ERROR не фильтруются.
Unix seconds сессий преобразуются в milliseconds до сортировки и отображения.
Строка лога использует только собственный timestamp с timezone: время другой
задачи или mtime файла ей не присваивается. Неизвестное время показывается как
`time unknown`, а не «только что». У `Runtime snapshot` дата относится к обновлению
снимка, не к моменту выполнения показанной задачи/результата. Лента не доказывает
текущую занятость воркера.
Частота обращений и последний запрос по профилям доступны отдельно в Grafana
**Hermes Overview → Profile requests**, см. [описание метрик](../README.md#production-контур-мониторинг-audit-и-метрики).

По умолчанию показаны **Task reports** — отчёты рабочих миссий. В селекторе
**Report source** отдельно доступны **Installation checks** (сохранённые
`Managed Swarm installation smoke check`) и **Runtime snapshots**. Последние —
записанное состояние runtime, а не live-проверка процесса или готовности TUI;
они не увеличивают счётчики рабочих отчётов. История не удаляется и задания
автоматически не перезапускаются.

Карточка показывает **Latest report** по времени, а не самую старую ошибку
с максимальным приоритетом. Предыдущие Blocked остаются в **History** и
**Open reports**; новая успешная проверка не делает старый сбой несуществующим.
Счётчики относятся к записям выбранного источника и фильтров, не к числу агентов.
Board использует те же фильтры; для runtime-снимков доступны Cards/List.

**Unique files** считает уникальные указанные пути в отчётах воркера, не previews
и не число упоминаний. `none`, `N/A`, `[]` и `—` не являются файлами. Историческая
миссия не наследует артефакты другой текущей задачи. Список основан на сообщении
воркера, а не подтверждает реальные изменения файлов. Проверяйте diff отдельно.
Исправление включено в managed build-wrapper: очередной deploy пересоберёт UI;
до deploy простого обновления вкладки недостаточно.

## Задачи из Telegram и субагенты

Для Telegram используется нативный `delegate_task` Hermes, а не отдельные
постоянные воркеры Workspace. Ansible публикует правила в отдельном managed-блоке
`workspace/AGENTS.md`, сохраняет личные инструкции и включает блок в резервную
копию. Правила действуют и без Workspace или полномочий host admin.

### Автоматический командный цикл

Ansible устанавливает локальный plugin `team-workflow`. Он добавляет инструмент
`team_workflow` в штатный toolset `delegation`: если делегирование отключено
для платформы, инструмент не обходит это ограничение. Общая модель субагентов
остаётся из deploy-конфигурации; отдельные модели и новый gateway не нужны.

Для нетривиальной задачи главный агент выбирает режим: исследование, текст,
код, диагностика, планирование или общая задача. Простые вопросы — без команды.

```text
Запрос → цель и критерии → Researcher → Executor → Reviewer
                                         ↑          │
                                         └─ правки ─┤
                                                    └→ единый ответ в Telegram
```

Это последовательные нативные субагенты, **не три постоянных Swarm-воркера**.
Исследователь готовит проверяемый план, исполнитель создаёт результат,
независимый проверяющий читает сам артефакт/дифф и сверяет критерии. При замечаниях
запускается ограниченный цикл исправлений. Координатор проверяет итог и отвечает
в исходный чат/topic. Диагностика сама по себе не разрешает исправления.

Настройки `vps_hermes.config.managed_overlay.team_workflow`:

| Параметр | Политика по умолчанию |
|---|---|
| `enabled` | `true` — установка и включение при Ansible deploy |
| `max_revision_rounds` | 2 раунда исправлений после первой проверки |
| `deadline_seconds` | 1800 секунд; проверка на событиях и запросах статуса |

Состояние и отчёты сохраняются в `$HERMES_HOME/team-workflow/`, приватно для
пользователя Hermes. Допускается **одна командная задача на весь Hermes home**.
Другой запрос получает `busy`, а не обещание очереди; обычные чаты при этом
не блокируются. `start` с тем же `request_id` идемпотентен, но повторное
использование ID с другой целью отклоняется. `status` и `list` доступны владельцу
задачи; `cancel` останавливает только записанные нативные ID этой задачи.

Для кода создаётся отдельный detached worktree от committed HEAD репозитория
внутри `terminal.cwd`. Незакоммиченные изменения исходного checkout **не копируются**.
Полные текстовые результаты можно сохранять в `team-workflow/artifacts/<id>/`.
Worktree и отчёты не удаляются автоматически: после проверки ими управляет владелец.
После 1000 записей требуется ручное архивирование завершённых задач.

Исполнителям запрещены commit/push/deploy/restart, внешние сообщения и изменения
прав. Такие действия выполняет главный агент только при явном разрешении владельца.
Роли — инструкции, **не OS sandbox**; у субагентов остаются возможности родителя.

Каждое штатное completion-событие будит главного агента. Он вызывает `advance`,
а контроллер читает сохранённый результат Hermes, проверяет JSON/evidence и выбирает
следующий этап. Вердикт, переданный координатором на словах, не принимается.
При синхронном fallback Hermes результат обрабатывается сразу по `next_action`.
Пустой/невалидный/обрезанный ответ, исчерпание бюджета или отказ доступа не считаются
успехом. Сохранённые evidence — утверждения модели: их истинность проверяется
ревьюером и координатором, а не доказывается наличием JSON.

После сбоя подтверждённые состояния читаются с диска. Незавершённый нативный
запуск может завершиться ошибкой, а не продолжиться. Если потеряна квитанция
запуска (`dispatch_unknown`), повторный запуск и освобождение занятого места
запрещены до ручной проверки: нельзя угадывать, были ли уже внесены изменения.
`awaiting_coordinator` означает, что результат готов, но нужен `advance`.
После отмены поздний результат не запускает новый этап.

Это **не автономный демон**: дальнейшее продвижение зависит от completion-механизма
Hermes и вызова инструмента главным агентом. Отдельного watchdog, точного общего
таймаута и гарантии exactly-once доставки в Telegram нет. Текущий субагент дополнительно
ограничен штатным `child_timeout_seconds`. `/swarm` и `/conductor` не отображают
эти задачи автоматически.

### Штатное делегирование

Для отдельных независимых подзадач остаётся `delegate_task` с ролями исследователя,
разработчика, проверяющего или диагноста. Нельзя одновременно запускать его и
командный цикл для одной и той же работы.

Параметры в `vps_runtime.set` файла `config/vps-defaults.yml`:

| Параметр | Начальная политика |
|---|---|
| `delegation.max_concurrent_children` | 2 исполнителя в одном вызове; также ограничивает число фоновых единиц работы |
| `delegation.max_spawn_depth` | 1: без вложенных субагентов |
| `delegation.max_iterations` | 50 шагов на исполнителя |
| `delegation.child_timeout_seconds` | 900 секунд на исполнителя |
| `delegation.subagent_auto_approve` | `false`: не подтверждать опасные действия автоматически |

Это управляемые deploy-параметры, не UI-owned значения. Числовые бюджеты можно
изменять без правки тестов; текст инструкций получает их из той же конфигурации.
Один batch в upstream занимает одну async-единицу: параметр `2` **не гарантирует
два процесса на весь VPS**. Инструкции дополнительно запрещают перекрывающиеся
batch для одного запроса. Другие чаты могут работать одновременно. Ограничения
времени не являются гарантированным сроком доставки сообщения в Telegram.

Модель делегирования задаётся из общей deploy-политики (см. выше), независимо
от переопределения модели родителя в topic. Инструкции запрещают самовольное переключение моделей и платный
OpenRouter fallback. Read-only роли не являются технической изоляцией доступа:
субагенты наследуют возможности родителя, поэтому нельзя считать их sandbox.

Закреплённый [Hermes delegate tool](https://github.com/NousResearch/hermes-agent/blob/29112bef099274229cadff79cdff7bf7b99c4b77/tools/delegate_tool.py)
уже поддерживает фоновые задания и
[сохранение состояния и доставку completion](https://github.com/NousResearch/hermes-agent/blob/29112bef099274229cadff79cdff7b99c4b77/tools/async_delegation.py)
в исходную сессию. Мы используем этот механизм без второго gateway и без
поллеров. Инструкции требуют итог с доказательствами, явное сообщение об ошибке
и максимум один осмысленный повтор; это не новая гарантия доставки после любого
сбоя. `/swarm` и `/conductor` не получают автоматический мост к этим заданиям.

После обычного Ansible deploy проверьте в **новой Telegram-сессии**:

1. Задайте простой вопрос: Hermes должен ответить без субагентов.
2. Попросите две независимые read-only проверки, например: «Проверь последний
   CI run и отдельно изучи документацию обновления Hermes. Используй командный
   цикл с независимой проверкой. Не меняй файлы проекта, настройки или сервисы.
   Верни ссылки и единый итог». Это вызывает модельные
   запросы и может расходовать квоту.
3. Во время работы запросите состояние командной задачи (`team_workflow status`)
   и список текущих субагентов. Это обращение к инструменту агента, **не CLI-команда**.
   `/status` сам по себе не показывает весь командный цикл. Сверяйте
   реальные задачи/ID, а не количество персонажей в Office. Быстрые задачи
   могут завершиться раньше запроса статуса.
4. Дождитесь итогового ответа **без дополнительного запроса** в том же topic.
   Статус `dispatched` не является успешным завершением. Если ответ не пришёл,
   нужны диагностика completion/delivery и журнал gateway, а не новый поллер.
5. Отдельно проверьте отмену тестовой задачи: агент должен запросить остановку
   собственных детей, не перезапускать их и не выдавать отмену за успех.

Эти проверки требуют работающего VPS/провайдера; локальные тесты конфигурации
и шаблонов не подтверждают качество делегирования или доставку в Telegram.

## Проверка и отключение

```bash
sudo systemctl status hermes-workspace.service hermes-gateway.service hermes-dashboard.service
sudo journalctl -u hermes-workspace.service -n 100 --no-pager
tailscale serve status
```

Playbook проверяет доступность gateway API по TCP и HTTP-ответ Workspace.
Это не заменяет ручную проверку входа, чата, сохранения настроек и Office
после первого развёртывания. Office — представление upstream, не гарантия
отображения всех native Telegram subagents в реальном времени.

Локальный smoke-тест pinned upstream, собранного с managed build-wrapper,
можно повторить без VPS
и без реальных credentials (используются временный Hermes home и fake backend):

```bash
WORKSPACE_UPSTREAM_DIR=/absolute/path/to/built/hermes-workspace \
  python3 -m unittest hermes/runtime/test_workspace_upstream.py
```

Он проверяет реальный Node entry, вход Workspace, отказ без Dashboard-сессии,
проксирование Sessions/Skills/Jobs, POST Jobs и отдельные заголовки ротации cookies.
MCP CRUD и Test проверяются как при успешном `/api/status`, так и при его `503`:
запросы остаются на Dashboard, без сессии возвращается `401`.
Сам по себе он не проверяет доступность провайдера OAuth или поведение live VPS.

Известная особенность закреплённого upstream: неавторизованный запрос к
`/api/hermes-config` и его legacy alias возвращает HTTP 500 вместо 401.
После входа маршрут отвечает штатно; 500 до входа не следует трактовать как
падение Hermes gateway. Остальные проверенные защищённые маршруты возвращают 401.

Для отключения задайте `workspace_ui: false` и выполните обычный deploy:
служба остановится и будет отключена, а managed Serve-конфигурация уберёт её
endpoint. Исходники и пользовательские данные не удаляются. Общий API может
оставаться включённым в `config.yaml` для других клиентов; перед отключением
`platforms.api_server.enabled` убедитесь, что они его не используют.
